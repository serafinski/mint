# Proposal vs. Implementation — Comparison

**Source proposal:** `docs/thesis_proposal.md` (Feb 2026)
**Implementation snapshot:** `iter/6-execution-backends`, April 2026
**Purpose:** Side-by-side audit so we can decide which deviations stay, which get reverted, and which need to be acknowledged in the thesis.

Legend:
- ✅ **Faithful** — implementation matches the proposal
- ⭐ **Strengthened** — implementation goes **beyond** the proposal in a way that improves the thesis claim (e.g., closes a bypass the proposal didn't anticipate, makes a proposal claim more measurable). These are the additive *good* deviations and should be foregrounded in the relevant chapter.
- 🟢 **Kept deviation** — either diverges from the proposal or is a deliberate implementation choice the proposal is silent on, and we have **explicitly decided to keep it** for this thesis (with justification + Ch 7 future-work note where relevant)
- 🟡 **Refined** — additive or defensible deviation, no explicit decision needed (typically infrastructure/tooling that doesn't change a thesis claim)
- 🔴 **Drift** — deviation that needs an explicit decision (keep, revert, or write up as limitation)
- ❌ **Missing** — proposed item that is not implemented at all

## TL;DR

The **architecture** (3 pillars, 4 baselines, retry loop, Pydantic state contracts, Docker sandbox) is largely faithful to the proposal. After walking the doc end-to-end, the gap between proposal and implementation collapses into **one big open question, two small pre-eval code bundles, and a pile of post-eval aggregation work — most of which is already DECIDED.** A focused action list lives in `docs/todo_drift_and_missing.md`.

**The one big open question:**

1. **Per-gap classification + compositional execution** (rows 4b, items #1/#9) — proposal says "per-gap, with matched capabilities reused"; implementation does per-task and rebuilds matched capabilities from scratch (T14 reproducer: csv-parser matched, then re-implemented inside the generated aggregator). Sequencing call: **ship the compositional fix before the eval** (clean reuse story, delays the eval) **or run the eval on the current pipeline** (inflated reuse counts, Ch 6 needs caveats). 🔴

**The pre-eval code work** (~120 lines, both DECIDED, one focused commit):

2. **Tier 1 hardening bundle** (item #3, ~75 lines) — adds `unittest.mock` / `random.seed` / `faker` / lorem-ipsum AST checks, plus a SKILL/AGENT code-fence scanner that lifts the existing AST checks onto code blocks inside markdown artifacts. Converts the current MCP_TOOL-only scoping from a limitation into a deliberate layered design.
3. **Tier 2 latency rename + variance check** (item #4, ~45 lines) — renames the existing 5s timeout check away from the `latency` category and adds the proposal's actual mock-smell check (3-5 runs, flag if `mean<1ms` AND `cv<0.10`).

**The post-eval aggregation work** (all DECIDED, three of the six proposal metrics not yet produced by `analyze_results.py`):

4. **Mock-contamination audit** (~5 h, item #7) — most important Pillar 2 metric, the only one that measures the gate's false-negative rate
5. **Gini coefficient on longitudinal store** (~1 h, item #5)
6. **KL divergence surfacing in eval analysis** (~1 h, item #6) — DECIDED: point-mass primary, histogram as sensitivity check (Option C); bundled with a ~5-line function rename to force the API distinction

**Pure prose / chapter work** (no code, happens during drafting): reword Ch 6 to drop "ML model training" (item #8, the testbed is correct, the proposal language was loose), prune the Ch 3 tech-stack table (item #10 — drop Google ADK / A2A / TS MCP / TOML / Claude-Code-as-runtime; add DeepAgents, DuckDB ⭐, LangFuse ⭐, three execution backends ⭐), and reframe the Tier 1 scoping in Ch 4 once item #3 lands.

**The Pillar 3 optimizer is the most faithful subsystem** — utility formula, thresholds, type scoping, and KL convergence detection all match the proposal. The main tech-stack drift is the abandonment of speculative items the proposal listed (Google ADK, A2A, TypeScript MCP, TOML config) — all of these turned out to be either alternatives the proposal explicitly allowed (✅ Faithful) or aspirational language with no payoff at the testbed scale (🟢 Kept deviation). The two genuinely additive choices that *strengthen* the thesis claims are **DuckDB** (load-bearing for Pillar 3 metrics) and **LangFuse** (delivers the token-cost metric directly) — both ⭐ Strengthened.

### Structured State Communication

- **Proposal:** "Strictly typed JSON schemas representing the world state at each handoff point."
- **Implementation:** 18 Pydantic models in `src/schemas/` with `model_config = {"extra": "forbid"}`, used for every inter-node hand-off.
- **Verdict:** ✅ Faithful — and well-executed.

### Pipeline graph

`src/orchestrator/pipeline.py` builds: `decomposition → gap_detection → classifier → generate_mcp_tool → generate_skill → generate_agent → verification_node → loading_node [→ optimizer_node]`. The proposal's 5-stage description maps cleanly onto this. The three generators are wired as a **sequential filter chain** rather than a parallel fan-out via the LangGraph `Send` API: each generator node iterates `state.classified_gaps` filtered by its own `CapabilityType` (`mcp_tool.py:339`, `skill.py:355`, `agent.py:325`), so only the generators with matching gaps actually do LLM work — the others invoke as nodes but immediately return on an empty filter result. 🟢 Kept deviation — deliberate simplicity choice that the proposal is silent on. Sequential is easier to debug and trace; the cost is one no-op node invocation per unused type per task (negligible). Worth one sentence in Ch 3 §3.5 to head off "why isn't this parallel via Send?" reviewer questions.

**Type scoping (a post-pilot refinement):** Tier 1's AST + regex checks currently run **only on `MCP_TOOL` source code** (`gate.py:54-76`, documented in CLAUDE.md). Skills get a Tier 0 `quick_validate.py` structural check only; agents get a regex pass over their JSON config. The scoping was added because regexes for words like `mock`/`placeholder` produced false positives on legitimate skill prose ("do not leave placeholder values"), blocking T04 in the pilot.

🔴 → **fix planned (Option E + F bundle)**: SKILL and AGENT artifacts have *executable* portions (code blocks inside markdown) that should be statically scanned, and *natural language* portions that should not. The fix is to **extract Python code fences** from these artifacts and run the existing MCP_TOOL AST checks (`_check_hardcoded_return`, `_check_silent_except`, `_check_missing_external_calls`) against each extracted snippet. Prose is excluded by construction, so the T04-style false positives cannot recur.

Concrete dispatch:

- **SKILL** → extract fences from `skill_content` (the SKILL.md body)
- **AGENT** → extract fences from `system_prompt` **and** from `skill_content` if `is_deep_agent=True` (verified in `agent.py:264-287`: a generated AGENT may carry a full SKILL.md alongside its system_prompt, validated through the same `validate_skill_content` pipeline as regular skills, and written to `data/eval/skills/<name>/SKILL.md` on disk — so AGENT is structurally a superset of SKILL)

Plus a small **Option F** complement: extend Tier 0 (`quick_validate.py`) with a tiny set of high-precision content checks against SKILL.md / AGENT prose: lorem ipsum literal, literal `TODO: implement`, literal `# placeholder return` — patterns that are *never* legitimate in skill prose regardless of context. ~10 lines, near-zero FP risk.

Bundle size: ~50 lines of code + tests, MCP_TOOL Tier 1 machinery reused unchanged. After landing, retag 🟢 with this Ch 4 framing: **"Tier 1 scopes its AST/regex checks to the executable portions of each artifact: Python source for MCP_TOOL, code-fenced snippets for SKILL/AGENT. Prose-level cheating ('the skill instructs the LLM to fabricate data') is out of scope for Tier 1 by design and is caught by Tier 2's behavioral consistency tests and Tier 3's adversarial probing instead."** This converts the current scoping from a *limitation* into a *deliberate layered design*.

Out of scope for Tier 1 (relegated to Tier 2/3): prose-level fabrication instructions, base64-encoded blobs, NLU-style cheating detection. Prose-level NLU would require an LLM-driven scanner, which violates the Tier 1 contract (fast + deterministic) and collapses Tier 1 into Tier 3.

### Tier 3 — Adversarial Probing

`adversarial.py` is a `create_deep_agent()` invocation with `sandbox_execute` as its only tool, structured output via `AdversarialFindings`, fresh per call, `recursion_limit=50`, 300s timeout, fail-open on timeout/error. The system prompt instructs the agent to run **all three** attack patterns (hidden demo mode, network unavailable via `--network none`, ground-truth comparison). ✅ Faithful in design.

**Caveat:** Because the agent is autonomous, there is no hard guarantee it actually executes all three attacks on every artifact — the system prompt is the only enforcement. Worth a note in Ch 4.

### Verification gate cost ladder

`gate.py` implements: Critical → block immediately, High → run Tier 2, Tier 2 Critical/High → block, then Tier 3, then merge findings. ✅ Matches the proposal's tiered cost structure.

### Retry loop

`verification_node.py` enforces `MAX_ATTEMPTS=3` and re-runs failed generators with the verification feedback injected into the next generation prompt before failing open. The proposal is silent on retry depth and on the feedback-injection mechanism. 🟢 Kept deviation — deliberate engineering choice that the proposal does not specify but that materially affects the Pillar 1 claim: without retry-with-feedback, a single Pydantic validation failure or a single Tier 1 hit would terminate generation, dragging the success rate down. With it, the generator gets one chance to interpret the failure and produce a corrected artifact. Cap at 3 keeps token cost bounded. Worth one paragraph in Ch 3 §3.5 (and a sentence in Ch 6 noting that retry is part of the JIT pipeline's success-rate story).

## Evaluation Strategy

### Testbed

**Proposal:** "Business Analytics Pipeline — data ingestion from heterogeneous sources, data transformation, **ML model training, inference**, and report generation."

**Implementation:** 18 tasks (T01–T18), 7 file formats (CSV, JSON, TXT, YAML, XML, Excel, TSV), 32 fixture files, three tiers (trivial/moderate/complex). Tasks cover ingestion, transformation, statistical analysis, anomaly detection, root-cause inference. **Notably absent:** no scikit-learn / no model `.fit()` call / no actual supervised learning. T06 ("KNN imputation") and T10 ("sales forecasting") are deterministic statistical methods, not model training in the proposal's sense.

🟢 Kept deviation — **the proposal language was loose; the testbed is correct.** Day-to-day business analytics in real organisations is dominated by SQL aggregations, dashboards, statistical reports, anomaly detection, and forecasting via deterministic methods (Prophet, ARIMA, exponential smoothing). Modern ML training is a *specialised* data-science workflow done on dedicated platforms (Databricks, SageMaker, Vertex AI), not in the ad-hoc "analyst answers a question" loop the testbed targets. The thesis is about capability *synthesis*, not about ML; adding an ML task to satisfy the proposal's word choice would be optics-driven scope creep, not substantive evaluation, and would make the 18-task set less internally consistent.

**Ch 6 prose rewrite (planned):** replace "data ingestion from heterogeneous sources, data transformation, **ML model training, inference**, and report generation" with "data ingestion from heterogeneous sources, data transformation, statistical analysis, anomaly detection, root-cause inference, and reporting". Describe the testbed accurately rather than inheriting the proposal's aspirational vocabulary.

**Separate concern (not the same issue):** does the existing AGENT-type coverage (5 of 18 tasks, including T17) adequately exercise the AGENT type's distinguishing features (multi-step planning, file-based context, iterative sandbox use)? If yes, the testbed is done. If AGENT tasks are mostly linear workflows that SKILL could handle, AGENT coverage is thin and worth addressing — see decision-table item #11.

## Cross-Cutting Things the Proposal Did Not Anticipate

These all came out of building the system. They are not in the proposal but matter for the thesis story:

1. **DeepAgents harness (LangChain package).** Used in 3 places: task decomposition, adversarial probing, AGENT execution. Provides built-in `write_todos`, file-based context management, subagent support, summarization. The proposal does not mention it — it is additive, and the model we run inside it is the same `gpt-5-mini` we use everywhere else. Worth a paragraph in Ch 3 §3.5 because it changes *how* Pillar 1 stage 1 and Pillar 2 Tier 3 are implemented.

2. **Three distinct execution backends.** Per CLAUDE.md: MCP_TOOL → Docker no-LLM, SKILL → constrained LLM with `bind_tools` capped at 3 tool calls, AGENT → full DeepAgent with `skills=` for progressive disclosure. The proposal treats execution as undifferentiated. Making the classifier's choice have *runtime consequences* is actually a stronger version of the thesis claim and should be foregrounded in Ch 3.

3. **Multi-artifact waste.** The pipeline generates **all three** artifact types on every task and only executes one. Wastes tokens; pollutes the registry. Tracked in `memory/project_multi_artifact_waste.md`. A remediation direction is under discussion but not yet finalized. Ch 6/7 implication.

4. **Loading-node pandas bug.** Tools that import pandas fail importlib registration but still execute via the sandbox — they run for the current task but never reach the registry for reuse. Tracked in `memory/project_loading_node_bug.md`.

5. **T16 ambiguity finding.** Not a bug, a *finding*: the test prompt is direction-agnostic ("changed first") and the LLM reasonably wrote a dual-criterion detector that disagreed with the single-direction ground truth. This is the "correct by policy, wrong by ground truth" failure class — exactly the kind of thing Pillar 2 cannot catch and that Ch 4 should call out as a limitation. Reproducibility check is queued.

6. **Tier 1 false-positive incident.** Pre-pilot, regex checks against words like "placeholder" in skill prose were blocking valid skills (T04). The fix was to scope Tier 1 to MCP_TOOL Python source. Worth reporting pre/post Tier 1 false-positive rates in Ch 4/6.

7. **Sandbox dependency resolution.** The proposal does not discuss how generated code's pip dependencies are resolved. Implementation: generator declares `pip_packages`; fallback is LLM-based name → PyPI mapping. Two-phase Docker (network → no network). Worth a Ch 3 paragraph.
